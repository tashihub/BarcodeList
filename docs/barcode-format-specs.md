# 対応バーコード仕様まとめ

このドキュメントは、今回のスコープで作成対応する全バーコード形式(既存5種 + 新規8種)の技術仕様を、実装に必要な範囲でまとめたもの。

種別は大きく「1次元(線状)バーコード」と「2次元バーコード」に分かれる。

> **2026-07-06追記:** 当初「要検証」としていた UPC-E / MSI / Plessey は、`ZXing.Net`側の挙動(チェックデジットの自動付与有無、UPC-Eの正しい入力形式)が未確認でリスクがあるため、**読み取り・作成とも対象外**とすることを決定した。詳細は末尾の「対象外」セクションを参照。

---

## 既存対応(実装済み・参考)

### QRコード(QrCode)
- 2次元。数字・英数字・バイナリ(日本語含む)を混在してエンコード可能。
- 長さ制限は誤り訂正レベルとエンコードモードに依存(実用上は数百〜数千文字まで可能)。
- チェックデジットの概念はなく、シンボル自体にリードソロモン誤り訂正が内蔵されている。
- 現状は無検証で保存(空文字チェックすらしていない)。

### Code 39
- 1次元。文字種: `0-9` `A-Z`(大文字のみ) 半角スペース `- . $ / + %`。可変長。
- 前後にスタート/ストップ文字(`*`)が必要だが、エンコーダが自動付与するため入力データに含める必要はない。
- チェックデジット(mod43)は規格上オプションで、現状未実装(多くの現場運用でも省略される)。

### Code 128
- 1次元。3つの文字セット(A/B/C)を自動切替し、フルASCII(0-127)をエンコード可能。Cセットは数字2桁ずつを高密度格納。
- チェックデジット(mod103)はエンコーダが自動計算・付与するため利用者側での対応不要。
- 可変長。現状の実装はASCII文字のみに制限(日本語などの非ASCIIは不可、エラーメッセージでQRへの誘導をしている)。

### EAN-13
- 1次元。数字13桁固定(データ12桁+チェックデジット1桁)。
- チェックデジット計算: 先頭(1桁目)を重み1、以降1桁ごとに重み1と3を交互(2桁目=3, 3桁目=1, ...)。
  `sum = Σ(digit_i × weight_i)`、`check = (10 - sum % 10) % 10`。
- 既存実装(`Ean13CreateService`)で正しく実装済み。

### GS1-128
- 1次元。物理的には Code 128 だが、先頭にFNC1(GS1フラグ)が入り、スキャナ側がシンボロジ識別子 `]C1` として認識する点が通常のCode128と異なる。
- データはAI(Application Identifier, 2〜4桁)+値の連続。可変長AIが末尾以外に来る場合はGS(`(char)29`)で区切る。
- `ZXing.Common.EncodingOptions.GS1Format = true` を設定してCode128としてエンコードすることで実現する(実機検証済み、詳細は [spec-gs1-and-barcode-expansion.md](spec-gs1-and-barcode-expansion.md) 参照)。

## 新規対応: 数字+チェックデジット系

### EAN-8
- 1次元。数字8桁固定(データ7桁+チェックデジット1桁)。小型商品向けのEAN-13短縮版。
- チェックデジット計算: 1桁目から重み `3,1,3,1,3,1,3`(EAN-13と重みの開始が逆になる点に注意)。
  `check = (10 - sum % 10) % 10`。
- 例: データ `4017072` → `sum = 4*3+0*1+1*3+7*1+0*3+7*1+2*3 = 35` → `check = 5` → 完成形 `40170725`。

### UPC-A
- 1次元。数字12桁固定(データ11桁+チェックデジット1桁)。北米向け小売標準、EAN-13の先頭に`0`を付けたものと等価。
- チェックデジット計算: 1桁目から重み `3,1,3,1,3,1,3,1,3,1,3`。`check = (10 - sum % 10) % 10`。
- 例: データ `03600029145` → `sum=58` → `check=2` → 完成形 `036000291452`。

## 新規対応: 数字のみ・可変長系

### ITF(Interleaved 2 of 5)
- 1次元。数字のみ。**桁数は偶数でなければならない**(実機検証済み: 奇数桁は`ArgumentException`で拒否される)。2桁ずつペアにしてバー/スペースに変換する方式のため。
- 標準のITF自体にはチェックデジットは無いが、物流でよく使われる「ITF-14」という派生規格は14桁固定+mod10チェックデジット(EAN/UPCと同系の重み3/1交互)を持つ。ITF-14として運用したい場合は、桁数14固定+チェックデジット計算を追加で行う。

---

## 新規対応: 英数記号系

### Codabar
- 1次元。文字種: 数字`0-9`、記号`- $ : / . +`、およびスタート/ストップ文字(`A/B/C/D`のいずれか、前後に必要)。図書館の貸出カードや血液バッグ、一部運送業(旧FedEx)で使用。
- **検証済み**: `ZXing.Net`はスタート/ストップ文字を含めない入力(`123456`)でもエラーにならず、含めた入力(`A123456A`)も通った。含めない場合にライブラリ側でどう補完しているかは不明なため、意図した記号で運用したい場合は明示的にスタート/ストップ文字を入力に含めることを推奨する。
- チェックデジットは規格上任意で、実運用でも省略されることが多い(未対応で問題ない)。

### Code 93
- 1次元。Code 39の後継規格で、より高密度。シフト文字を使ってフルASCII(128文字)をエンコード可能。可変長。
- チェック文字(C・K の2種類、mod47ベース)は規格上必須だが、エンコーダが自動計算・付与するため利用者側の対応は不要。

---

## 新規対応: 2次元・自由入力系

### Data Matrix
- 2次元。正方形/長方形のモジュールパターン。ECC200という誤り訂正方式が標準。最小10×10〜最大144×144モジュール程度まで可変。
- 数字のみなら最大約3116桁、英数字なら約2335文字、バイナリなら約1556バイトまで格納可能(シンボルサイズ上限に依存。正確な上限は実装依存のため目安)。
- チェックデジットの概念はなく、Reed-Solomon誤り訂正が内蔵。医薬品・電子部品の小型印字でよく使われる。

### PDF417
- 2次元(スタック型、複数行の1次元的コードを積み重ねた構造)。大容量データ向け(最大約1800バイト/2700桁程度、誤り訂正レベル0〜8を選択可能)。
- 身分証明書・搭乗券・物流ラベルなどで使用。チェックデジットの概念はなく、誤り訂正レベルに応じた冗長コードワードが自動付与される。

### Aztec
- 2次元。中心に特徴的な「ブルズアイ(同心正方形)」のファインダーパターンを持ち、周囲にクワイエットゾーン(余白)が不要という特徴がある。搭乗券や乗車券でよく使われる。
- サイズ・誤り訂正率(パーセント指定)が可変。チェックデジットの概念はなく誤り訂正符号が内蔵。

---

## 対象外(読み取り・作成とも非対応)

以下3形式は、実運用での需要が低いこと、かつ`ZXing.Net`側の挙動(チェックデジットの自動付与有無、正しい入力形式)が未確認でリスクがあることから、**読み取り・作成のいずれも対象外**とする(2026-07-06決定)。

- **UPC-E**: UPC-Aの圧縮版。圧縮ルールが複雑で、`ZXing.Net`が期待する入力形式(6/7/8桁のどれで何を渡すべきか)が未確認。
- **MSI(Modified Plessey)**: チェックデジット方式が規格として統一されておらず、`ZXing.Net`が自動付与するかも未確認。
- **Plessey**: 現在ほぼ使われない古い規格で、チェックサムの自動付与有無も未確認。

読み取り側は、`BarcodeReaderView` の `BarcodeReaderOptions.Formats` を `BarcodeFormats.All` から、この3形式を除いた値に変更する必要がある(`ZXing.Net.Maui.BarcodeFormat` は `[Flags]` 列挙体なので、`BarcodeFormats.All & ~(BarcodeFormat.Msi | BarcodeFormat.Plessey | BarcodeFormat.UpcE)` のようなビット除外で実現できる)。

## 実装時の共通注意点

- チェックデジットをエンコーダが自動計算する形式(Code39のスタート/ストップ、Code128、Code93など)は、アプリ側でチェックデジットの入力や計算をユーザーに求める必要はない。
- チェックデジットを利用者側で計算して埋め込む必要がある形式(EAN-8/13, UPC-A)は、既存の`Ean13CreateService`と同様のパターンで実装する。
